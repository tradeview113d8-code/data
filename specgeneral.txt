6. REPO 3 — DATA / LOGIC BOUNDARY
The interaction system is deliberately separated into static possibility data and runtime execution.
STATIC DATA
│
├── events
├── emotion_actions
├── actions
├── social_effects
├── character-emotion profiles
└── character-pool
        │
        ▼
      ENGINE
        │
        ├── context
        ├── scoring
        ├── weighted selection
        ├── target resolution
        ├── state
        ├── seed
        └── loop / termination
        │
        ▼
ACTUAL PATH
6.1 Interaction Data
events
│
└── Event
    └── Role
        └── Emotion Distribution
emotion_actions
│
└── Emotion
    └── Context Role
        └── Action Distribution
The same Action may appear under many different emotions.
This is intentional.
guilt
├── apologize
├── help
└── withdraw

fear
├── withdraw
├── seek_help
└── confront

anger
├── confront
├── blame
└── withdraw
Action duplication across emotion contexts is acceptable.
The system prioritizes clarity of each emotion's action set over deduplicating the data.
actions
│
└── Action
    ├── social_effect_id
    └── target_rule
social_effects
│
└── Social Effect
    └── Target Emotion Distribution

9. RUNTIME STOP CONDITIONS
The Interaction Loop does not run indefinitely.
STOP
│
├── max_depth reached
├── no valid action
├── terminal / termination signal
├── loop protection
└── engine-specific pruning
Runtime owns these decisions.
Static data does not contain branch state.
10. MULTI-CHARACTER EXECUTION
The static data does not create one hardcoded branch for every possible character.
EVENT
│
├── Character A
├── Character B
├── Character C
└── Character D
Runtime resolves actual participants.
TARGET RULE
     │
     ▼
TARGET RESOLUTION
     │
     ▼
ACTUAL CHARACTER
Therefore:
STATIC
INTERACTOR
can become at runtime:
CHAR_A
CHAR_B
CHAR_C
...
without duplicating the dictionary.

18. FINAL PRINCIPLE
The World Simulator is not:
REAL WORLD → LLM → STORY
It is:
REAL WORLD
    ↓
DATA EVOLUTION
    ↓
WORLD DNA
    ↓
LIVING WORLD
    ↓
EVENT
    ↓
ROLE
    ↓
EMOTION
    ↓
CHARACTER
    ↓
ACTION
    ↓
SOCIAL EFFECT
    ↓
TARGET
    ↓
NEW SOCIAL EVENT
    ↓
INTERACTION LOOP
    ↓
MICROSCENE
    ↓
NARRATIVE ASSEMBLY
    ↓
EPISODE
    ↓
PRESENTATION
    ↓
MEDIA
The central simulator loop is therefore:
EVENT
 ↓
EMOTION
 ↓
ACTION
 ↓
SOCIAL EFFECT
 ↓
TARGET
 ↓
NEW EVENT
 └──────────────→ REPEAT
while the surrounding system evolves the resulting data from immutable World DNA into living World State and finally into World History.
STATUS MODEL
Every item in the TreeGeneral should carry one of these statuses when maintained in the project:
IMPLEMENTED
    = executable source file exists and has been tested

SPECIFIED
    = execution contract exists but source is not yet implemented

DATA
    = knowledge/configuration artifact maintained by Human + Chatbot

TESTED
    = implementation has an observed successful execution

PENDING
    = identified but not yet specified/implemented
The TreeGeneral itself is the map.
The SPEC defines the contract.
The source file executes the contract.
The data supplies the knowledge.
The runtime produces the actual evolving world.
