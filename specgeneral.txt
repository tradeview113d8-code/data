# 0. SYSTEM IDENTITY

WORLD SIMULATOR

├── REPOSITORY 1 — STATIC WORLD DATA
├── REPOSITORY 2 — DYNAMIC WORLD DATA

## Mục tiêu

World Simulator không phải là:

```text
REAL NEWS → LLM → STORY
```

Mà là:

```text
REAL WORLD
    ↓
WORLD DATA
    ↓
DYNAMIC EVENT DATA
    ↓
NEWS-GEAR
    +
CHARACTER-GEAR
    ↓
PYTHON STATE-TRANSITION ENGINE
    ↓
CHARACTER STATES
    ↓
CHARACTER ACTIONS
    ↓
INTERACTION
    ↓
ACTUAL PATH / TRACE
    ↓
MICROSCENES
    ↓
NARRATIVE PRODUCTION
    ↓
EPISODE
```

Bản chất của hệ thống là một **state-transition simulation** có xác suất:

```text
STATE(t)
   +
INPUT / ACTION
   +
CHARACTER PARAMETERS
   ↓
DELTA
   ↓
STATE(t+1)
```

và tiếp tục lặp khi còn điều kiện tương tác.

# 1. THUẬT NGỮ CỐT LÕI

Các thuật ngữ như `NEWS-GEAR`, `CHARACTER-GEAR`, `GEARBOX` là **domain language / metaphor** dùng để mô tả các thành phần của hệ thống.

Chúng không phải các cấu trúc dữ liệu đặc biệt.

## 1.1 NEWS-GEAR

**Technical meaning:**

```text
Structured Event Parameters
```

NEWS-GEAR là dữ liệu sự kiện đã được chuyển thành dạng mà Python có thể sử dụng để tính state.

Nó có thể chứa:

```text
event
actors / affected roles
actions
emotion impact
polarity
magnitude
affected dimensions
other event parameters
```

NEWS-GEAR không phải engine.

NEWS-GEAR không tự chạy.

```text
RAW NEWS
   ↓
LLM + Prompt + NEWS-GEAR Skeleton
   ↓
NEWS-GEAR JSON
   ↓
Python
```

---

## 1.2 CHARACTER-GEAR

**Technical meaning:**

```text
Character Parameter Set / Behavioral Coefficient Vector
```

Character-Gear là tập các hệ số tương đối ổn định của một nhân vật.

Ví dụ:

```text
emotion sensitivity
behavior bias
action affinity
risk tolerance
aggression baseline
trust baseline
empathy
fear sensitivity
pride
social response tendencies
...
```

Character-Gear không phải một worker.

Nó không chứa engine.

Nó không tự chuyển động.

Nó là **các hệ số khiến cùng một tác động tạo ra state khác nhau ở các nhân vật khác nhau**.

Ví dụ:

```text
NEWS IMPACT = +1.0 fear

CHAR_A sensitivity = 1.0
→ Δfear = +1.0

CHAR_B sensitivity = 0.4
→ Δfear = +0.4

CHAR_C sensitivity = 0.1
→ Δfear = +0.1
```

Vì vậy metaphor "bánh răng" chỉ có nghĩa:

> Mỗi nhân vật có bộ hệ số khác nhau, giống như các bánh răng có kích thước/tỷ lệ truyền khác nhau.

---

## 1.3 GEARBOX

**Technical meaning:**

```text
Python State-Transition Engine
```

GEARBOX không phải một file dữ liệu.

GEARBOX là code Python thực hiện:

```text
read input
→ calculate delta
→ update state
→ select action
→ resolve target
→ apply impact
→ update another state
→ repeat
```

Lõi toán học:

```text
S(t+1) = S(t) + Δ
```

Trong đó:

```text
Δ = f(
    input/action,
    character parameters,
    current state,
    target,
    interaction rules,
    randomness
)
```

GEARBOX là phần **quay các dữ liệu GEAR**.

---

## 1.4 ACTUAL PATH

**Technical meaning:**

```text
Ordered Execution Trace
```

Actual Path là chuỗi kết quả thực tế mà engine đã thực hiện.

Ví dụ:

```text
A received event
→ A felt fear
→ A chose confront
→ B received impact
→ B felt anger
→ B chose withdraw
→ ...
```

Về implementation, nó có thể chỉ là:

```python
[
    step_0,
    step_1,
    step_2,
    ...
]
```

Tên `Actual Path` được giữ vì đây là dữ liệu đầu ra dùng cho narrative layer.

---

## 1.5 MICROSCENE

**Technical meaning:**

```text
Narrative rendering of an interaction segment
```

Microscene không phải một state.

Không phải một node của behavior tree.

Không phải một nhánh cứng của gearbox.

Nó là cách biểu diễn bằng ngôn ngữ của một đoạn Actual Path.

# 7. THE STATE-TRANSITION MODEL

**STATUS: CORE DESIGN VALIDATED**

The central mechanism is:

```text
INPUT
 ↓
CHARACTER STATE
 ↓
DELTA CALCULATION
 ↓
NEW STATE
 ↓
ACTION
 ↓
IMPACT ON OTHER CHARACTER
 ↓
OTHER CHARACTER STATE
 ↓
ACTION
 ↓
...
```

The fundamental causal law is:

```text
NHẬN GÌ?
    ↓
CẢM THẤY GÌ?
    ↓
HÀNH ĐỘNG GÌ?
    ↓
TÁC ĐỘNG ĐẾN AI?
    ↓
NGƯỜI ĐÓ NHẬN GÌ?
    ↓
CẢM THẤY GÌ?
    ↓
HÀNH ĐỘNG GÌ?
```

This is the actual "gearbox" logic.

# 8. LAYER 1 — EXTERNAL NEWS IMPACT

**STATUS: TESTED**

Layer 1 is special because its input comes from outside the character system.

```text
NEWS-GEAR
    ↓
CHAR_A → STATE_A
CHAR_B → STATE_B
CHAR_C → STATE_C
CHAR_D → STATE_D
CHAR_E → STATE_E
```

The same news is applied to multiple characters.

Different Character-Gear parameters produce different state changes.

The dry-run explicitly demonstrated this: the same NEWS-GEAR generated different emotion states for the five characters because of different sensitivity parameters. fileciteturn123file6L794-L812

Therefore:

```text
SAME NEWS
+
DIFFERENT CHARACTER PARAMETERS
=
DIFFERENT STATES
```

# 9. LAYER 2+ — INTERNAL INTERACTION LOOP

**STATUS: TESTED IN LIMITED DRY-RUN / FINAL FLEXIBLE FORM PENDING**

From this point the input is no longer external news.

The new input is a character action.

```text
CHARACTER A ACTION
       ↓
IMPACT
       ↓
CHARACTER B STATE CHANGE
       ↓
CHARACTER B ACTION
       ↓
IMPACT
       ↓
CHARACTER A / C / D / E STATE CHANGE
       ↓
...
```

Therefore:

> At Layer 1, "news" means the real-world event.  
> From Layer 2 onward, a character's action becomes the next effective input.

This is the mechanism that allows an event to evolve into an interaction rather than remaining a static event replay.

# 10. THE THREE-LAYER DRY-RUN IS NOT THE FINAL ARCHITECTURE

**STATUS: TEST SCENARIO ONLY**

The previously executed:

```text
Layer 1
Layer 2
Layer 3
```

was a **data validation scenario**.

It proved:

```text
same news
→ different states
→ character interaction
→ state changes
```

It does NOT mean the final system must stop at three layers.

The final engine is:

```text
while interaction_is_valid:
    select actor
    calculate current state
    select action
    select target
    apply impact
    update target state
    continue / terminate
```

The number of interactions is determined by the simulation state and termination rules.

Therefore:

```text
3 layers ≠ architecture
3 layers = current test depth
```

# 11. FLEXIBLE INTERACTION SELECTION

**STATUS: TARGET DESIGN / PARTIALLY IMPLEMENTED**

The final system should not contain a fixed script such as:

```text
A → B
B → A
A → B
```

Instead Python should be able to determine from the current state:

```text
WHO should interact?
WHAT action is available?
WHO should be affected?
HOW strong is the effect?
SHOULD another character enter?
SHOULD an existing conflict reverse direction?
SHOULD the interaction stop?
```

Possible decision inputs:

```text
current emotional states
emotion polarity
state intensity
character coefficients
action affinity
target compatibility
current interaction context
previous actions
loop guards
random seed
```

This allows:

```text
A attacks B
→ C intervenes

or

B withdraws
→ A redirects attention to C

or

C unexpectedly supports B
→ A changes state

or

a seemingly resolved conflict
→ another character reactivates it
```

These are not pre-written story branches.

They emerge from the interaction state and the selection rules.

### Important boundary

Python determines:

```text
who interacts
what action occurs
what target is selected
what state changes
what causal consequence follows
```

LLM later determines:

```text
how the interaction is expressed in language
what words are spoken
how the scene is described
```

Thus "dialogue selection" in the simulation means Python can determine the **dialogue/action intent**, while LLM renders the actual spoken language.

# 12. RANDOMNESS AND UNEXPECTED TURNS

**STATUS: TESTED**

Randomness is part of the simulation mechanism.

It does not mean uncontrolled randomness.

```text
STATIC RULES
+
CHARACTER PARAMETERS
+
CURRENT STATE
+
SEEDED RANDOMNESS
=
ONE VALID PATH
```

Same:

```text input
+
characters
+
seed
```

should reproduce the same path.

Different seed may produce a different valid path.

The dry-run demonstrated deterministic replay and variance between seeds.

Therefore unexpected turns can emerge without LLM inventing the causal structure.

---

# 13. WHAT "CREATIVE" MEANS IN THE SIMULATOR

The simulator's creativity is not:

```text
LLM invents a plot.
```

It is:

```text
many valid states
+
many valid actions
+
different character parameters
+
target selection
+
weighted randomness
+
interaction feedback
=
many possible paths
```

The resulting path may contain a turn that was not explicitly written beforehand.

That is the intended form of computational emergence.

# 26. STATIC INTERACTION DICTIONARY

**STATUS: IMPLEMENTED / TESTED**

The current four-zone structure remains valid:

```text
events
emotion_actions
actions
social_effects
```

## events

```text
Event
 └── Role
      └── Emotion Distribution
```

## emotion_actions

```text
Emotion
 └── Context Role
      └── Action Distribution
```

The same action may intentionally occur under multiple emotions.

This duplication is accepted because clarity of each emotion's action set is more important than data deduplication. fileciteturn123file4L662-L690

## actions

```text
Action
 ├── social_effect_id
 └── target_rule
```

## social_effects

```text
Social Effect
 └── Target Emotion Distribution
```

This static dictionary defines **possibility space**.

It does not contain the actual path of a particular run.

# 28. RUNTIME

**STATUS: IMPLEMENTED IN DRY-RUN / REFINED TERMINOLOGY**

Runtime means:

```text
current execution state of the Python simulation
```

It is not:

```text
NEWS-GEAR
CHARACTER-GEAR
ACTUAL PATH
MICROSCENE
```

A runtime instance contains the temporary state required to execute one simulation:

```text
current actors
current states
current targets
current actions
depth / step
seed / RNG state
loop guards
context
history
```

The runtime is an implementation concept.

It should not be mistaken for another static data library.

# 29. WHAT THE DRY-RUN PROVED

**STATUS: TEST EVIDENCE**

The dry-run demonstrated:

```text
same NEWS-GEAR
+
different Character-Gear
=
different initial states
```

It also demonstrated that character actions can modify other characters' states, allowing the simulation to continue across interaction steps. fileciteturn123file6L794-L812

The important conclusion is not:

```text
"three layers work"
```

but:

```text
NEWS
  ↓
STATE DIFFERENTIATION
  ↓
ACTION
  ↓
STATE IMPACT
  ↓
FURTHER ACTION
```

This validates the core coupling between the News side and Character side.

# 35. FINAL DESIGN PRINCIPLE

The system is intentionally simple at its mechanical core.

```text
INPUT
 ↓
STATE
 ↓
DELTA
 ↓
ACTION
 ↓
IMPACT
 ↓
NEW STATE
 ↓
ACTION
 ↓
...
 ↓
TRACE
 ↓
NARRATIVE
```

The complexity does not come from adding more architectural layers.

It comes from the **combination space**:

```text
many characters
×
many states
×
many actions
×
many targets
×
different coefficients
×
different interaction contexts
×
seeded randomness
```

That combination can produce paths that were not manually scripted.

The final goal is therefore **not a fixed three-layer story**.

The three-layer dry-run was only a proof-of-mechanism.

The intended final system is a flexible interaction engine in which Python can select:

```text
WHO interacts
WHAT they feel
WHAT they do
WHO receives the action
HOW the receiver changes
WHETHER another character enters
WHETHER the direction reverses
WHEN the interaction stops
```

The LLM subsequently renders the selected causal path into:

```text
dialogue
description
emotion expression
scene language
narration
```

Thus:

```text
PYTHON
= determines the evolving causal path

LLM
= expresses that path as language
```

And the final narrative is not pre-written.

It is the result of:

```text
REAL NEWS
+
WORLD DATA
+
CHARACTER PARAMETERS
+
STATE TRANSITIONS
+
CHARACTER INTERACTIONS
+
WEIGHTED RANDOMNESS
+
NARRATIVE RENDERING
```

# 36. STATUS DEFINITIONS

```text
IMPLEMENTED
= source exists and is operational

TESTED
= an executable test has produced observable results

DATA
= knowledge/configuration artifact maintained by Human + Chatbot

SPECIFIED
= execution contract exists

PARTIAL
= some implementation exists but complete worker is unfinished

IN DEVELOPMENT
= architecture is established and implementation is being expanded

PENDING
= identified work not yet implemented
```

The General specification must never claim that a `SPECIFIED`, `PENDING`, or `IN DEVELOPMENT` component is already production-ready.
